# 技術仕様書 (Architecture Design Document)

作成日: 2026-08-19
工程: 基本設計 — **システム構造・技術選定**
正本参照: 要件は [`product-requirements.md`](./product-requirements.md)、機能設計は [`functional-design.md`](./functional-design.md)

> 本プロダクトはサーバー・DB を持たない**クライアント完結型のブラウザゲーム**。
> ビルド成果物（静的ファイル）を配信するだけで動作する。

## テクノロジースタック

### 言語・ランタイム

| 技術 | バージョン |
|------|-----------|
| Node.js（開発時のみ） | v22 LTS |
| TypeScript | 5.x |
| npm | 10.x |
| 実行環境 | モダンブラウザ（WebGL2 + WASM 対応。Chrome / Edge / Safari / Firefox の現行版） |

### フレームワーク・ライブラリ

| 技術 | バージョン | 用途 | 選定理由 |
|------|-----------|------|----------|
| Three.js | 0.16x（導入時の最新安定版） | 3D 描画 | WebGL の事実上の標準。ドキュメント・実績が最多で、コマと椀状トコ程度のシーンには十分軽量 |
| @dimforge/rapier3d-compat | 0.14+ | 物理エンジン | WASM 製で高速。決定的シミュレーションが可能でテスト再現性を確保できる。compat 版はバンドラ非依存で Vite と相性が良い |
| （UIフレームワーク） | なし | 画面・HUD | 画面5フェーズの状態機械で足りる。React 等はバンドル増と複雑化に見合わない |

**主要な比較検討**:

- **Three.js vs Babylon.js**: Babylon は物理統合が手厚いが本体が大きい。初回ロード 10 秒以内
  （PRD NFR）を優先し、必要機能だけ組み合わせられる Three.js を採用
- **Rapier vs cannon-es / ammo.js**: cannon-es はメンテ頻度と精度で劣り、ammo.js はビルドが重い。
  Rapier は活発に保守され決定性オプションがあり、回転体の衝突に必要な精度を持つ
- **Unity(WebGL) 不採用**: ビルドサイズが数十 MB 級になり「開いて10秒」と両立しない

### 開発ツール

| 技術 | バージョン | 用途 | 選定理由 |
|------|-----------|------|----------|
| Vite | 6.x | ビルド・開発サーバー | 高速な HMR。静的ビルド出力が配布要件に合致 |
| Vitest | 3.x | ユニット/統合テスト | Vite と設定共有。純粋ロジックのテストが軽い |
| Playwright | 1.x | E2E テスト | クロスブラウザで UC-01 を自動確認できる |
| ESLint + Prettier | 最新安定版 | 静的解析・整形 | 汎用規約（kit）準拠 |
| GitHub Actions | - | CI/CD | lint・test・build を PR ごとに実行し、main マージで GitHub Pages へデプロイ |

## アーキテクチャパターン

### レイヤードアーキテクチャ

```
┌──────────────────────────────┐
│  UIレイヤー (src/ui/)          │ ← 画面(フェーズ)表示・HUD・入力受付
├──────────────────────────────┤
│  ゲームロジックレイヤー (src/game/) │ ← 進行管理・投擲変換・判定・CPU（純粋）
├──────────────────────────────┤
│  エンジンレイヤー (src/engine/)   │ ← 物理(Rapier)・描画(Three.js)のラッパ
└──────────────────────────────┘
```

#### UIレイヤー（`src/ui/`）

- **責務**: フェーズごとの画面表示（DOM オーバーレイ）、Pointer Events による入力受付、HUD 更新
- **許可される操作**: ゲームロジックレイヤーへのイベント送出・状態購読
- **禁止される操作**: 物理・描画（エンジンレイヤー）への直接アクセス

#### ゲームロジックレイヤー（`src/game/`）

- **責務**: フェーズ状態機械、投擲変換・回転減衰・勝敗判定・CPU 投擲（機能設計書のアルゴリズム）、コマ3種の定義
- **許可される操作**: エンジンレイヤーの抽象インターフェース呼び出し
- **禁止される操作**: DOM・Three.js・Rapier への直接依存（**このレイヤーは import しない**。テスト対象の主眼のため純粋に保つ）

#### エンジンレイヤー（`src/engine/`）

- **責務**: Rapier ワールドの構築・固定タイムステップ更新、Three.js シーンの構築・描画、物理→描画の状態同期
- **許可される操作**: Rapier / Three.js / WebGL API の使用
- **禁止される操作**: ゲームルール（勝敗・減衰量の決定）の実装

## データ永続化戦略

### ストレージ方式

| データ種別 | ストレージ | フォーマット | 理由 |
|-----------|----------|-------------|------|
| 対戦状態・コマ状態 | メモリのみ | TypeScript オブジェクト | 1プレイ完結。永続化要件なし（PRD スコープ外） |
| コマ種別定義（3種） | ソースコード内静的定義 | TS 定数 | 外部データ化するほどの規模でない。型で守れる |

**永続化・バックアップは行わない。** localStorage 等の利用は将来（戦績記録 P2）まで導入しない。

## パフォーマンス要件

### レスポンスタイム

| 操作 | 目標時間 | 測定環境 |
|------|---------|---------|
| 初回ロード → タイトル表示 | 3 秒以内 | 4G 相当回線 |
| 初回ロード → プレイ可能 | 10 秒以内 | 4G 相当回線（PRD NFR） |
| 対戦中フレームレート | 30fps 以上 | ミドルレンジのスマホ実機 |
| 決着 → 勝敗表示 | 1 秒以内 | 全環境 |

### リソース使用量

| リソース | 上限 | 理由 |
|---------|------|------|
| 転送サイズ（初回・圧縮後） | 3 MB | 4G で 10 秒以内ロードの余裕をみた上限 |
| メモリ | 300 MB | ミドルレンジスマホのタブクラッシュ回避 |

## セキュリティアーキテクチャ

### データ保護

- **暗号化**: 対象データなし（個人情報・機密を扱わない）
- **アクセス制御**: 静的ホスティングの公開コンテンツのみ。管理系エンドポイントなし
- **機密情報管理**: ランタイム秘密情報なし。デプロイ用トークンは GitHub Actions のリポジトリシークレットのみで管理し、ソース・ドキュメントに書かない

### 入力検証

- **バリデーション**: ドラッグ座標を数値範囲でクランプ（投擲変換アルゴリズム内）
- **サニタイゼーション**: ユーザー文字列入力なし。`innerHTML` への動的文字列挿入を禁止し、DOM API（textContent）で表示する
- **エラーハンドリング**: 例外メッセージ・スタックを画面に出さない（cross-cutting.md のエラー表示文言のみ）

## スケーラビリティ設計

### データ増加への対応

- 剛体は常時2個（＋床）で増加しない。データ増加の懸念なし
- 同時アクセスは静的配信のためホスティング側でスケールする

### 機能拡張性

- **ラウンド制（P1）**: MatchStateMachine の `result` → `aiming` 遷移にラウンドカウンタを足すだけで拡張できる構造にする
- **ローカル対戦（P1）**: CPU 投擲モジュールと同一インターフェース（`ThrowProvider`）で人間2人目を差し替えられるようにする
- **オンライン対戦（P2）**: 物理を決定的シミュレーション＋入力同期で拡張する前提を保つ（乱数のシード注入はこの布石でもある）

## テスト戦略

> 詳細は [`docs/specs/_shared/cross-cutting.md`](../specs/_shared/cross-cutting.md)「テスト戦略」を正本とする。

- **ユニットテスト**: Vitest。`src/game/` の純粋ロジック全部。カバレッジ目標: `src/game/` で 90%
- **統合テスト**: Vitest + Rapier ヘッドレス実行（描画なし・固定シード）
- **E2Eテスト**: Playwright。UC-01 の1本通し＋WebGL 非対応フォールバック

## 技術的制約

### 環境要件

- **ブラウザ**: WebGL2 と WASM が有効なモダンブラウザ。非対応時はフォールバック表示（UC-04）
- **開発環境**: Node.js v22 LTS / npm 10.x
- **必要な外部依存**: なし（実行時に外部サービスへ接続しない）

### パフォーマンス制約

- 物理は固定タイムステップ 60Hz。1描画フレームでの追い付きステップは最大3回に制限
- 3D アセットはプリミティブ生成中心とし、外部テクスチャ・モデルは転送サイズ上限内でのみ追加

### セキュリティ制約

- 実行時の外部送信は行わない（計測導入時は本書を先に改訂する）
- 依存パッケージは lockfile 固定、CI で `npm audit` を実行

## 依存関係管理

| ライブラリ | 用途 | バージョン管理方針 |
|-----------|------|-------------------|
| three | 3D 描画 | package.json でマイナー固定（`~`）。破壊的変更が多いため慎重に上げる |
| @dimforge/rapier3d-compat | 物理 | マイナー固定（`~`）。挙動が変わるとゲームバランスに影響するため |
| vite / vitest / playwright / eslint / prettier | 開発ツール | 範囲指定（`^`）。lockfile で実体は固定 |
