# テーブル設計ワークフロー 実践ガイド

このガイドは、要件・PRD を起点にゼロからテーブルを設計するための実践的な手順を提供します。
フェーズの全体像・委譲先の一覧は `SKILL.md` を参照してください。本ガイドは**各フェーズの中身を
どう詰めるか**の手法です。

## このワークフローが満たすべき性質（共通）

1. **正本を重複させない** — 概念モデルは `docs/baseline/functional-design.md`、論理設計の判断は
   `logical-data-model.md`、物理スキーマは `table-definition.md`。同じ事実を2箇所に書かない。
   下流は上流を**参照**し、再定義しない。
2. **判断には理由を残す** — キー方式・正規化の崩し方・削除方針・区分値の表現は、いずれも
   「なぜそうしたか」が後から必ず問われる。結論だけを書かない。
3. **曖昧な先送りを残さない** — 「物理設計で確定」「実装時に判断」は使えない。
   `docs/specs/3_detail-design/` は詳細設計そのもので、先送り先が無い。
4. **上流から順に更新する（逆流ルール）** — 後からの変更でも、概念 → 論理 → 物理の順で更新する。
   物理だけ直すと上流が陳腐化し、次の設計判断が壊れた前提の上に載る。

## フェーズ1: 概念設計

**出力**: `docs/baseline/functional-design.md`「データモデル」
**委譲先**: `baseline-functional-design` スキル

### ステップ1: 要件から名詞を拾う

`docs/specs/1_requirements/requirements-definition.md`（無ければ `docs/baseline/product-requirements.md`）
を読み、**業務上の名詞**を列挙する。この時点では粒度を揃えなくてよい。

拾った名詞を次の3つに仕分ける。

| 分類         | 判定                                   | 扱い                     |
| ------------ | -------------------------------------- | ------------------------ |
| エンティティ | 独立して識別でき、ライフサイクルを持つ | 概念モデルに載せる       |
| 属性         | 単独では存在せず、何かに従属する       | そのエンティティの属性へ |
| 区分値       | 取りうる値が有限に列挙できる           | `[EnumType]` として定義  |

### ステップ2: 永続化するかを判定する

**すべてのエンティティをテーブルにするとは限らない**。外部 API から都度取得する、計算で導出できる、
セッション内にしか存在しない、といったものは永続化しない。

| 判定         | 質問                                                               |
| ------------ | ------------------------------------------------------------------ |
| 永続化する   | アプリを再起動しても保持している必要があるか                       |
| 永続化しない | 外部情報源から都度取得するか。他の永続データから計算で導出できるか |

永続化しないエンティティも概念モデルには載せる（ドメインの語彙として必要）が、
**フェーズ2以降の対象からは外す**。どれが永続対象かをこの段階で明示すること。

### ステップ3: 関連とカーディナリティを確定する

エンティティ間の関連ごとに、両方向から問う。

- 「`A` 1件に対して `B` は何件ありうるか（0件か、1件か、複数か）」
- 「`B` 1件に対して `A` は何件ありうるか」

両方向とも「複数」なら多対多。解決方法はフェーズ2で決める（ここでは多対多のまま記録する）。
**「0件ありうるか」を必ず確認する**こと。これが後の NULL 可否・外部キーの向きに直結する。

### ステップ4: ER図と確定事項を書く

`baseline-functional-design` スキルのテンプレートに従い、mermaid `erDiagram` で書く
（属性は日本語の論理名）。あわせて概念レベルの確定事項（日付/TZ の基準、削除方針の方向性、
一意性の単位）を残す。

> **このフェーズの完了条件**: 永続対象のエンティティが確定し、それぞれの関連とカーディナリティに
> 「たぶん」が残っていないこと。ここが揺れると以降すべてが揺れる。

## フェーズ2: 論理設計 ★このスキルが直接担当する

**出力**: `docs/specs/3_detail-design/db/logical-data-model.md`
**テンプレート**: [`./templates/logical-data-model.md`](./templates/logical-data-model.md)

概念モデルを、物理スキーマに落とせる形まで具体化する。**物理型は書かない**（フェーズ3の担当）。
以下の9ステップを順に確定させる。ステップ番号はテンプレートの章番号と一対一で対応する。

> **対象は永続化するエンティティのみ**。フェーズ1ステップ2で「永続化しない」と判定したものは、
> 本フェーズの全ステップの対象外になる。冒頭で対象／対象外を明記してから始めること。

#### 既存プロジェクトへの遡及適用（`table-definition.md` が先行して存在する場合）

論理設計フェーズが無かった時期に作られた `table-definition.md` は、本来ここに属する判断
（主キー方式を選んだ理由・レコード数の制約とその担保方法・削除方針・文字数上限の根拠など）を
**設計メモやカラムの説明欄にインラインで抱えている**ことが多い。ゼロから起こす場合と手順が違うため、
次の順で整理する。

1. **抽出** — 既存 `table-definition.md` を読み、論理設計に属する記述を洗い出す。
   典型的な在りか: 「設計メモ（確定事項）」の各項目、カラム定義表の「説明」列に混ざった判断理由、
   索引不要の設計判断を述べた注記。
2. **仕分け** — 抽出した各項目を「論理（判断と理由）」と「物理（実装上の決めごと）」に分ける。
   判断に迷ったら次を基準にする。

   | 論理へ移す | 物理に残す |
   |---|---|
   | なぜその主キー方式か | 主キーの物理型（UUID/BIGSERIAL） |
   | レコード数の制約と、どこで担保するか | その制約を表現する物理制約名 |
   | 削除方針（物理削除/論理削除/削除しない）とその理由 | `ON DELETE` の指定 |
   | 値域・文字数上限を「その値」にした根拠 | CHECK 制約の物理名と条件式 |
   | 区分値をその表現方法にした理由 | CHECK 制約の列挙値 |
   | — | `updated_at` の更新方式、DB バージョン依存の関数、索引の用途 |

3. **作成** — 仕分けた「論理」側を本テンプレートへ流し込み、`logical-data-model.md` を作成する。
   このとき**埋まらない章が出てくる**（当時決めずに済ませていた項目）。それが遡及適用で見つかる
   設計の穴であり、この場でユーザーと確定させる。
4. **整理** — `table-definition.md` 側から移し終えた記述を削り、必要なら
   「正本は `logical-data-model.md`」への参照に置き換える。**両方に残さない**。
5. **逆流の確認** — 抽出の過程で概念モデル（baseline）にも書かれていない前提が見つかったら、
   逆流ルールに従って baseline から順に直す。

### ステップ1: 属性を洗い出す

エンティティごとに属性を列挙し、**論理データ型**（文字列・数値・日時・真偽・列挙）と必須/任意を決める。

このとき、`docs/specs/2_basic-design/screen-design.md`（画面の項目）と `api-design.md`（APIの入出力）を
突き合わせ、**その属性がどこから必要になったか（導出元）を必ず記録する**。

- 画面にもAPIにもFRにも出てこない属性 → 本当に必要か疑う
- 画面には出るが属性が無い項目 → 属性の漏れ、または他の属性から導出できるか確認する

> 「必須/任意」は業務上の話。物理的な NOT NULL 制約に落とすかはフェーズ3で決める
> （必須だがアプリ層でのみ担保する、という選択もありうる）。

### ステップ2: キーを設計する

**主キー方式の選択**:

| 方式                         | 向いている場面                                               | 注意点                                               |
| ---------------------------- | ------------------------------------------------------------ | ---------------------------------------------------- |
| サロゲートキー（UUID・連番） | ほとんどの場合の既定選択。業務的な意味を持たないIDを別に持つ | 業務上の一意性は別途 UNIQUE 制約で担保する必要がある |
| ナチュラルキー               | 業務上の識別子が不変かつ確実に一意（規格化されたコード等）   | 業務側の都合で値が変わると全参照が壊れる             |
| 複合キー                     | 中間エンティティで、関連そのものが識別子になる場合           | 参照する側の外部キーが複数列になり扱いが重くなる     |

UUID と連番の選択は、外部に露出するか（連番は件数や他レコードの存在が推測できる）、
分散生成が必要か、を基準にする。

**公開識別子**: 主キーを URL・API レスポンスなど**外部から見える場所にそのまま出すか**を決める。
出さないなら、外部向けの識別子を別に持つ。連番主キーをそのまま URL に出すと、
件数や他レコードの存在が推測できてしまう点に注意する。

**候補キー・一意性の単位**: 「何が重複してはいけないか」を業務ルールとして列挙し、
それを表現する属性の組を決める。**ルール自体の正本は要件定義書の FR**。ここには対応づけだけを残す。
一意性の制約が無いなら「なし」と明記する。

**レコード数の制約**: 「常に1件のみ」「ユーザーあたり最大N件」のように、レコード数そのものに
業務上の制約がある場合は、それを**どこで担保するか**まで決める。

| 担保する場所 | 向いている場面 | 書くべきこと |
|---|---|---|
| DB制約（UNIQUE等） | 確実に破られては困る | どの制約でどう表現するか（物理制約名はフェーズ3） |
| アプリケーション層 | DB制約では素直に表現できない（「常に1件」など） | DBを直接操作されれば破れることを承知の上での判断であること、その前提（信頼された単一クライアントのみがアクセスする等） |

「常に1件」を DB で強制するのは意外と面倒（定数列＋UNIQUE などの技巧が要る）。
**アプリ層に委ねる判断自体は妥当だが、「防げない」ことを明示的に受け入れた記録を残す**のが重要。

### ステップ3: 所有者・テナントを決める

各エンティティについて「そのレコードは**誰のもの**か」を決める。ここが決まっていないと、
所有権チェック（自分のデータだけを操作できること）を実装する足場が無くなる。

**所有者列の後付けは、この工程で最も高くつく修正**になる。テーブルが確定してから足すと、
全クエリ・全マイグレーション・既存データの移行を伴う。正規化やキー設計と同じ重さで扱うこと。

| 所有者の表現 | 向いている場面 | 注意点 |
|---|---|---|
| 所有者列（`user_id` 等）を直接持つ | 利用者ごとにデータが分かれる | 全ての取得・更新クエリに所有者条件が必要 |
| 親を辿って判定する | 親子関係が明確で、子が単独で参照されない | JOIN を挟むぶん**所有権チェックの書き漏らしが起きやすい**。2段以上辿るなら所有者列の冗長保持（ステップ4の意図的な非正規化）を検討する |
| 全体共有（所有者なし） | マスタデータ、単一利用者向けアプリ | **全利用者が読めてよいことを明記する**。「まだ決めていない」との区別が付かなくなるため、必ず理由を書く |

担保する場所（アプリ層のクエリ条件か、DB の行レベルセキュリティか）もあわせて決める。

> 単一ユーザー向けアプリで「所有者なし」を選ぶのは妥当な判断だが、**選んだことを記録する**。
> 将来マルチユーザー化する際に、どこから手を付ければよいかがこの記述で決まる。

### ステップ4: 正規化する

第3正規形までを目標に整理する。各エンティティについて確認する。

- **第1正規形** — 繰り返し項目・カンマ区切りの複数値を持つ属性が無いか
- **第2正規形** — 複合キーの一部にしか依存しない属性が無いか
- **第3正規形** — 主キー以外の属性に依存する属性が無いか（推移的関数従属）

**意図的に崩す場合**は、次の3点をセットで書く。1つでも書けないなら採用しない。

1. どこを崩すか（どのエンティティのどの属性）
2. なぜ崩すか — 「どのアクセスパターンが、正規化したままだと何が問題になるか」を具体的に
3. どう整合を保つか — 更新経路の一本化、再計算のタイミング、不整合検知の方法

崩していないなら**「なし」と明記する**（空欄で放置しない）。

### ステップ5: 関連を解決する

フェーズ1で確定したカーディナリティを、実装可能な形に落とす。
**永続化エンティティが1つだけ、または関連が無い場合も「関連なし」と明記する**（節ごと省略しない）。
後から読む人が「検討漏れ」と「検討した結果なし」を区別できなくなる。

| カーディナリティ | 実装方法                                                                                                                 |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 1対多            | 「多」側に外部キーを持たせる                                                                                             |
| 多対多           | 中間エンティティを新設する。関連自体が属性を持つ場合（開始日・役割など）は必ず中間エンティティ                           |
| 1対1             | 片方に外部キー＋UNIQUE、または同一テーブルへ統合。**分ける理由**（アクセス頻度差・機密度差・任意性）が無いなら統合を検討 |

**外部キーの向きと削除挙動**を決める。削除挙動はステップ7（削除方針）と**必ず整合させる**。
論理削除を採るなら物理的な `ON DELETE` はほぼ発火しない点に注意する。

### ステップ6: 区分値の持ち方を決める

**永続化エンティティが持つ区分値だけ**が対象。非永続エンティティの区分値（APIレスポンス上にしか
現れないもの）は DB 表現を決める必要がないため対象外で、その旨を明記する。
永続側に区分値が無ければ「該当なし」と書く。

対象となる区分値ごとに、CHECK制約付きの文字列 / 参照テーブル / DB の enum 型 から選ぶ。

| 観点                   | 判断                                                                                           |
| ---------------------- | ---------------------------------------------------------------------------------------------- |
| 運用中に値が増減するか | 増減する → 参照テーブル。仕様として固定 → CHECK 制約                                           |
| 値に付随情報が要るか   | 表示名・並び順・有効期間を持たせたい → 参照テーブル                                            |
| DB の enum 型を使うか  | 値の追加にマイグレーションが必要、削除・並べ替えが困難、移植性も下がる。採用するなら理由を明記 |

迷ったら CHECK 制約付きの文字列を既定とする（参照テーブルへの移行は後からでも可能だが、逆は面倒）。

### ステップ7: 履歴・監査・削除方針を決める

**削除方針** — エンティティごとに、物理削除 / 論理削除 / 削除しない を決める。判断材料:

- 法令・業務上、削除後も記録を残す必要があるか
- 参照している他のエンティティが、削除後も参照先の情報を必要とするか
- 論理削除を採る場合、**すべての検索クエリに削除済み除外の条件が付く**負担を受け入れられるか
- **逆向きの問い — 消せと言われたときに消し切れるか**。削除を求められたとき（利用者からの消去要求）、
  そのエンティティの個人情報を確実に消せるか。次のコピー先をすべて洗い出す。
  - 論理削除を採る場合、削除済みレコードに個人情報が残り続けてよいか（残すなら匿名化するか）
  - 履歴テーブルに複製された個人情報をどう扱うか
  - 監査項目（作成者/更新者）に残る個人識別子をどう扱うか

  「残す必要があるか」だけを問うと、この向きの検討が丸ごと抜ける。ステップ8の「コピー先」列と
  突き合わせて判断すること。

**監査項目** — 作成日時、更新日時、作成者/更新者、変更履歴のそれぞれについて要否を決める。
「全エンティティ共通で持つ」のか「一部だけ」なのかを明示する。

**作成日時と更新日時は別々に判断する**。両者をセットで持つのが一般的だが、
「レコードが起動時に1件作られてあとは更新しか起きない」ような設計では作成日時が無意味になる。
まとめて「タイムスタンプを持つ」と決めると、この判断が素通りする。

**業務データ以外も忘れない** — 認証失敗・権限拒否といった**セキュリティイベントの記録先**が
必要かを判断する。フェーズ1の名詞抽出は業務上の名詞だけを拾うため、この種のテーブルは
構造的に漏れる。不要なら「不要」と理由を書く。

**履歴テーブル** — 変更履歴を保持する場合のみ。記録タイミング（更新時/削除時）と保持期間、
期間経過後の扱いまで決める。不要なら「不要」と理由を書く。

あわせて**更新・削除の可否**（追記専用にするか）を決める。**監査目的の履歴が、アプリと同じ権限で
書き換えられるなら監査にならない**。追記専用にする場合、それを成立させる権限分離をフェーズ5で
申し送る。

### ステップ8: 個人情報・機密情報を識別する

後から設計に入れるのが難しいため、この段階で確定させる。

**「該当なし」と書く前に、次に一つでも当てはまらないことを確認する。**
一つでも当てはまるなら「該当なし」ではない。

- 利用者を識別できる属性がある（氏名・メールアドレス・電話番号・外部サービスのユーザーID・
  ハンドル名・アイコン画像のURL）
- ログイン・認証がある（パスワード・トークン・セッション識別子・外部IdPの subject）
- 利用者の行動・嗜好が記録される（閲覧履歴・お気に入り・位置情報）
- 他人に見られると困る自由記述がある

要件定義に非機能要件が無いプロジェクトほど、この章が空欄のまま素通りしやすい。
上のリストは、NFR が無くても最低限の判定ができるようにするための足がかり。

**確認すべき観点**:

- 認証情報を可逆な形で保存していないか
- ログ・エラーメッセージに出力されると問題になる属性はどれか
  （禁止と判定した属性は、ステップ9の次「物理設計への申し送り」でエラーハンドリング方針・
  API詳細設計へ引き継ぐ。**識別して終わりにしない**）
- 保持期間の定めがある属性はあるか（期間経過後の削除・匿名化の方法）
- **コピー先を漏らさず洗い出す** — 論理削除を選んだエンティティ、履歴テーブル、監査項目の
  作成者/更新者。本体を消しても、これらに複製された個人情報は残る（ステップ7の削除方針と往復する）
- 保存時に**暗号化**が必要な属性はあるか。必要なら**暗号化の単位**（カラム単位 / ストレージ・DB全体）と
  **鍵の管理場所**（誰が復号できるか）まで決める
  - **カラム単位の暗号化を採ると、その列は等値検索・部分一致・索引・ソートが効かなくなる**。
    検索が必要なら、検索用のハッシュ列を別に持つなどの設計をこの段階で決める。
    フェーズ3の索引設計に入ってから発覚すると論理まで逆流する

ここで識別した属性は、フェーズ4のセキュリティレビューの入力になる（`security-engineer` へ一覧を渡す）。

### ステップ9: 命名規約を決める

プロジェクト全体の命名規則の正本（`docs/baseline/development-guidelines.md`）を参照しつつ、
**データモデル固有の規則**だけをここで決める。

- 概念モデルの camelCase ↔ テーブルの snake_case の対応
- テーブル名の単複
- 主キー・外部キー・日時カラム・真偽値カラムの命名
- 中間テーブルの命名

**フェーズ3で迷わないための事前合意**が目的。ここが決まっていないと、物理設計で命名がぶれる。

## フェーズ3: 物理設計

**出力**: `docs/specs/3_detail-design/db/table-definition.md`
**委譲先**: `specs-detail-design` スキル

### ステップ1: 論理を物理へ対応づける

`logical-data-model.md` の各エンティティ・属性を、テーブル・カラムへ写す。

| 論理設計（フェーズ2）    | 物理設計（フェーズ3）                                   |
| ------------------------ | ------------------------------------------------------- |
| エンティティ             | テーブル（命名規約に従って snake_case へ）              |
| 属性＋論理データ型       | カラム＋物理型（`VARCHAR(100)`・`TIMESTAMPTZ` 等）      |
| 必須/任意                | NOT NULL 制約の有無（アプリ層でのみ担保する選択もある） |
| 値域・列挙               | CHECK 制約（物理制約名を付ける）                        |
| 一意性の単位             | UNIQUE 制約                                             |
| 外部キーの向き・削除挙動 | FK 制約＋`ON DELETE ...`                                |
| 削除方針（論理削除）     | 削除フラグ・削除日時カラム                              |

### ステップ2: 索引を決める（フェーズ4の結果を根拠にする）

索引は**アクセスパターンから導出する**。「とりあえず張る」をしない。
根拠となるアクセスパターンはフェーズ4の CRUD マトリクスで洗い出すため、
**フェーズ4を先に一度回してから索引を確定させてもよい**（この順序の前後は許容する）。

各索引について「どのクエリのために張ったか」を設計メモに残す。

### ステップ3: 設計メモを書く

`specs-detail-design` スキルのガイドに従う。ただし**論理設計の判断を再掲しない**
（キー方式の理由・正規化の崩し方・削除方針は `logical-data-model.md` が正本）。
設計メモに書くのは物理的な実装判断に限る。

- `updated_at` の更新方式（アプリケーション側で明示設定 / DBトリガー）
- DB バージョン依存の関数・型を使う場合の前提バージョン
- 索引の用途

## フェーズ4: 検証

設計の抜けを機械的に洗い出す。**ここで見つかった不足は、フェーズ1（概念）まで逆流して直す**。

### ステップ1: CRUD マトリクスを作る

主要なユースケース／API を行、テーブルを列にして、C（作成）R（参照）U（更新）D（削除）を埋める。

| ユースケース / API         | `[table1]` | `[table2]` | `[table3]` |
| -------------------------- | :--------: | :--------: | :--------: |
| `[UC-01] [ユースケース名]` |     C      |     R      |     —      |
| `[API-02] GET /api/[path]` |     R      |     R      |     —      |
| `[API-03] PUT /api/[path]` |     U      |     —      |     —      |

**このマトリクスで検出できる設計の穴**:

| 症状                                       | 疑うこと                                                   |
| ------------------------------------------ | ---------------------------------------------------------- |
| どの行にも C が無いテーブル                | データが作られない。初期投入か、そもそも不要か             |
| R しか付かないテーブル                     | マスタか、外部から取り込むデータか。更新経路は本当に不要か |
| どの行にも現れないテーブル                 | 使われていない。削除を検討する                             |
| D が無いのに論理削除を設計した             | 削除方針が過剰。フェーズ2に戻る                            |
| 1つのユースケースが多数のテーブルを U する | トランザクション境界が広い。整合性の担保方法を確認する     |

R が付いた組み合わせは、**索引の根拠**（フェーズ3ステップ2）になる。

### ステップ2: 項目充足チェック（双方向）

- **画面・API → スキーマ**: `docs/specs/2_basic-design/screen-design.md` の全画面項目、
  `api-design.md` の全レスポンスフィールドが、スキーマから導出できるか。導出できないものは属性の漏れ。
- **スキーマ → 画面・API**: どの画面にもAPIにも現れないカラムがあるか。あるなら本当に必要か。

### ステップ3: レビューを依頼する

構造とセキュリティは観点が異なるため、**並列で依頼する**。

| レビュー             | 依頼先エージェント      | 観点                                                                                       |
| -------------------- | ----------------------- | ------------------------------------------------------------------------------------------ |
| 構造レビュー         | `architecture-designer` | 正規化の妥当性、キー設計、関連の解決方法、拡張余地、アクセスパターンとの整合               |
| セキュリティレビュー | `security-engineer`     | 所有者・テナント分離と所有権チェックの担保、個人情報・認証情報の保存形式、削除要求時に消し切れるか（コピー先の網羅性）、監査ログの十分性と改ざん耐性、保持期間、DBロールの最小権限 |

セキュリティレビューには、次を入力として渡すこと。

- フェーズ2ステップ8で識別した個人情報・機密情報の一覧（コピー先・ログ出力可否の列を含む）
- フェーズ2ステップ3で決めた所有者・テナントの表現と、所有権チェックの担保場所

> **レビューで見つけても手遅れになる項目がある**。所有者列の有無はテーブル確定後に足すと
> 全クエリ改修になる。だからフェーズ2に書く欄を設けている。フェーズ4のレビューは
> **フェーズ2で埋めた内容の妥当性を問う場**であって、そこで初めて考える場ではない。

## フェーズ5: 実装への申し送り

### マイグレーション

物理 DDL（マイグレーション SQL）は**ドキュメントには書かない**。`table-definition.md` を基に、
マイグレーション実装のタイミングで生成する。使用するマイグレーションツールと管理方式は
`docs/baseline/architecture.md` の技術選定に従う。

### テスト工程への連携

| 検証内容                                                           | 委譲先                                                              |
| ------------------------------------------------------------------ | ------------------------------------------------------------------- |
| ドメインロジックのバリデーション（実DB不要）                       | `docs/specs/4_unit-test/`（`specs-unit-test` スキル）               |
| 制約・索引が実際に張られていることの確認、実DBを介した整合性の検証 | `docs/specs/5_integration-test/`（`specs-integration-test` スキル） |

**制約は「定義した」だけでは担保されない**。CHECK 制約・UNIQUE 制約・NOT NULL が実際に効いていることは、
**テスト用DBに対して**アプリ層をバイパスした直接 SQL を実行して確認する結合テストケースとして起こす。
この観点を結合テスト工程へ申し送る（本番DBへ直接 SQL を打つ運用を意味しない）。

### DBユーザー・権限の申し送り

マイグレーション実装へ、次のロール分離を申し送る（`docs/baseline/architecture.md` の技術選定と整合させる）。

| ロール | 権限 | 用途 |
|---|---|---|
| アプリケーション用 | 対象テーブルへの SELECT/INSERT/UPDATE/DELETE のみ | 実行時のデータ操作。**DDL 権限を与えない** |
| マイグレーション用 | DDL を含む | スキーマ変更時のみ。アプリの実行時接続には使わない |
| 読み取り専用（必要なら） | SELECT のみ | 調査・分析用 |

**ロール分離は、論理設計で置いた前提の裏付けになる**。

- フェーズ2ステップ2で「レコード数の制約はアプリ層で担保する」と決めた場合、
  それは**アプリ以外の接続経路が存在しないこと**を前提にしている
- フェーズ2ステップ7で履歴テーブルを「追記専用」と決めた場合、
  アプリケーション用ロールから当該テーブルの UPDATE/DELETE を外して初めて成立する

前提を置いただけで権限を分けなければ、その前提は成立しない。

### 個人情報の取り扱いの申し送り

フェーズ2ステップ8で**ログ出力禁止**と判定した属性の一覧を、エラーハンドリング方針
（`docs/specs/_shared/cross-cutting.md`）と API 詳細設計（`docs/specs/3_detail-design/api/`）へ申し送る。
識別しただけでは実装に届かない。

## まとめ

テーブル設計を成功させるポイント:

1. **概念 → 論理 → 物理の順に降り、逆流も同じ順で行う**（物理だけ直さない）
2. **判断には必ず理由を残す**（キー方式・正規化・削除方針・区分値の表現）
3. **正本を重複させない** — 下流は上流を参照し、再定義しない
4. **曖昧な先送りを残さない** — `3_detail-design/` に先送り先は無い
5. **CRUD マトリクスで機械的に穴を探す** — 目視のレビューでは漏れる
6. **個人情報の識別と所有者の設計は、この段階でやる** — どちらも後から入れるのが最も難しい。
   所有者列はテーブル確定後に足すと全クエリ改修になり、個人情報の取り扱いは
   コピー先（履歴・監査）が増えたあとでは追いきれなくなる
7. **前提を置いたら、それを成立させる手当てまで申し送る** — 「アプリ層で担保する」「追記専用にする」は、
   DBロールを分けて初めて成立する。前提の記述だけで終わらせない
