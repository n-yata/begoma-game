# テーブル設計ワークフロー

このスキルは、要件・PRD を起点にゼロからテーブルを設計するためのワークフローの入口です。
概念 → 論理 → 物理 → 検証 → 申し送り の5フェーズで進めます。

| フェーズ    | 入力                                | 出力                                                   | 担当                                                   |
| ----------- | ----------------------------------- | ------------------------------------------------------ | ------------------------------------------------------ |
| 1. 概念設計 | 要件定義書・PRD                     | `docs/baseline/functional-design.md`「データモデル」   | `baseline-functional-design` へ委譲                    |
| 2. 論理設計 | 概念モデル・画面/API の入出力       | `docs/specs/3_detail-design/db/logical-data-model.md`  | **本スキルが直接担当**                                 |
| 3. 物理設計 | 論理データモデル書                  | `docs/specs/3_detail-design/db/table-definition.md`    | `specs-detail-design` へ委譲                           |
| 4. 検証     | 物理スキーマ・ユースケース/API 一覧 | CRUD マトリクス・レビュー結果（不足はフェーズ1へ逆流） | 本スキル＋`architecture-designer`・`security-engineer` |
| 5. 申し送り | 確定した物理スキーマ                | マイグレーション実装・テスト工程への引き継ぎ           | `specs-unit-test`・`specs-integration-test` へ委譲     |

## このスキルの位置づけ（なぜ論理設計だけ自前か）

データモデルの正本は工程ごとに分かれている。

- **概念モデル**（エンティティ・区分値・ER図・ドメイン上の制約）— `docs/baseline/functional-design.md`。
  `baseline-functional-design` スキルが担当する**指標＝正本**。
- **物理スキーマ**（型・NULL可否・デフォルト・物理制約名・索引名）— `table-definition.md`。
  `specs-detail-design` スキルが担当する。

この2つの**間**にある判断 — キー設計（サロゲート/ナチュラル）、正規化とその意図的な崩し方、
多対多の解決、削除・履歴・監査の方針、区分値の表現方法（CHECK/参照テーブル/enum型）、
個人情報の識別、命名規約 — は、**概念モデルには具体的すぎ、物理スキーマの表形式には収まらない**。
担当スキルが存在しなかったため、本スキルが `logical-data-model.md` として引き受ける。

**結論だけでなく理由を残すこと**がこのフェーズの価値。キー方式や削除方針は、
後から「なぜそうしたか」が必ず問われる。

## 前提条件

開始する前に、以下が存在することを確認してください。

| 必要なもの | 本ワークフローでの使い道 | 無い場合の誘導先 |
| --- | --- | --- |
| `docs/baseline/product-requirements.md`（PRD） | フェーズ1でエンティティ候補の名詞を抽出する元 | `baseline-prd` スキル、または `/flow-setup-project` |
| `docs/specs/1_requirements/requirements-definition.md`（あれば望ましい） | 一意性ルール・整合規則の**正本**。フェーズ2で参照し、本書では再定義しない | `specs-requirements` スキル |
| `docs/specs/1_requirements/non-functional-requirements.md`（あれば望ましい） | フェーズ2ステップ7で個人情報の取り扱い・保持期間・監査要件を確認する | `specs-requirements` スキル |
| `docs/baseline/architecture.md` の DB 技術選定（DB製品・バージョン・マイグレーション方式） | フェーズ3の物理型・DB依存機能、フェーズ5のマイグレーション方式の前提 | `baseline-architecture-design` スキル |
| `docs/baseline/development-guidelines.md` | フェーズ2ステップ8の命名規約の**正本**（データモデル固有の規則だけを本書で決める） | `baseline-development-guidelines` スキル |

`docs/specs/2_basic-design/screen-design.md`・`api-design.md` は、フェーズ2の属性の洗い出しで
突き合わせる入力になる。まだ無い場合はフェーズ2を画面/API 設計と並行して進め、
**フェーズ4の項目充足チェックで必ず突き合わせる**こと。

> **`table-definition.md` が既に存在する場合**（論理設計フェーズが無かった時期に作られた）は、
> ゼロから起こすのとは手順が異なる。物理側にインラインで抱えている判断を抽出して
> `logical-data-model.md` へ移す**遡及適用の手順**を `guide.md` フェーズ2冒頭に用意しているので、
> そちらに従うこと。

## 進め方（要点）

### フェーズ1: 概念設計

1. 要件から業務上の名詞を拾い、エンティティ／属性／区分値に仕分ける。
2. **永続化するエンティティとしないエンティティを区別する**（外部から都度取得する、計算で導出できるものは永続化しない）。
3. 関連ごとに両方向のカーディナリティと「0件ありうるか」を確定する。
4. `baseline-functional-design` スキルで ER 図・確定事項を書く。

### フェーズ2: 論理設計（本スキルが担当）

**対象は永続化するエンティティのみ**（フェーズ1ステップ2で判定済み）。対象／対象外を冒頭で明記してから、
テンプレートの章順に次の9つを確定させる（章番号と `guide.md` のステップ番号は一対一で対応する）。

1. **属性の洗い出し** — 論理データ型（文字列/数値/日時/真偽/列挙）まで。**物理型は書かない**。
   各属性に「どこから必要になったか（導出元）」を記録する。
2. **キー設計** — 主キー方式の選択と理由、公開識別子（主キーを外部に露出するか）、候補キー、
   一意性の単位、レコード数の制約（「常に1件」等がある場合は、DB制約とアプリ層のどちらで担保するかまで）。
3. **所有者・テナントの表現** — 各エンティティが「誰のものか」と、所有権チェックの担保場所。
   **所有者列の後付けは全クエリ改修を伴う**ため、この段階で決める。単一利用者向けで
   「所有者なし」を選ぶ場合も、選んだことを記録する。
4. **正規化** — 第3正規形まで。崩す場合は「どこを・なぜ・どう整合を保つか」を必ずセットで書く。
5. **関連の解決** — 多対多の中間エンティティ化、外部キーの向き、削除挙動。
6. **区分値の持ち方** — CHECK制約 / 参照テーブル / enum型 の選択と理由。
7. **履歴・監査・削除方針** — 論理削除 vs 物理削除（**消せと言われたときに消し切れるか**も問う）、
   監査項目（作成日時と更新日時は別々に判断する）、セキュリティイベントの記録先、
   履歴テーブルの要否と追記専用にするか。
8. **個人情報・機密情報の識別** — 「該当なし」と書く前に判定リストを通す。取り扱い・保持期間・
   **コピー先**（履歴テーブル・監査項目）・ログ出力可否・暗号化の要否まで決める。
   フェーズ4のセキュリティレビューの入力になる。
9. **命名規約** — camelCase ↔ snake_case 対応、テーブル名の単複、主キー/外部キー/日時/真偽値カラムの
   命名。フェーズ3で命名がぶれないための事前合意。

### フェーズ3: 物理設計

`specs-detail-design` スキルへ委譲する。論理設計の各要素を物理へ対応づけ、型・制約・索引を決める。
**論理設計の判断（キー方式の理由・正規化・削除方針）を設計メモに再掲しない**
（正本は `logical-data-model.md`）。

### フェーズ4: 検証

1. **CRUD マトリクス** — ユースケース/API × テーブルで C/R/U/D を埋め、
   どの操作からも作られないテーブル・どこにも現れないテーブルを機械的に洗い出す。
   R が付いた組み合わせは索引の根拠になる。
2. **項目充足チェック（双方向）** — 画面項目・APIレスポンスがスキーマから導出できるか。
   逆に、どこにも現れないカラムが無いか。
3. **レビュー** — `architecture-designer`（構造）と `security-engineer`（所有者・テナント分離、
   個人情報、監査ログの改ざん耐性、DBロールの最小権限）に**並列で**依頼する。フェーズ2ステップ8で
   識別した個人情報の一覧と、ステップ3で決めた所有者の表現を入力として渡す。
   **レビューはフェーズ2で埋めた内容の妥当性を問う場**であり、そこで初めて考える場ではない。

**不足が見つかったらフェーズ1（概念）まで逆流して直す**。物理だけ直して辻褄を合わせない。

### フェーズ5: 実装への申し送り

- 物理 DDL（マイグレーション SQL）は**ドキュメントに書かない**。`table-definition.md` を基に、
  マイグレーション実装のタイミングで生成する（方式は `docs/baseline/architecture.md` の技術選定に従う）。
- **制約は「定義した」だけでは担保されない**。CHECK・UNIQUE・NOT NULL が実際に効いていることを、
  **テスト用DBに対して**アプリ層をバイパスした直接 SQL で確認する結合テストケースとして
  `specs-integration-test` へ申し送る。
- ドメインロジックのバリデーション（実DB不要）は `specs-unit-test` へ。
- **DBユーザー・権限の分離**（アプリケーション用 / マイグレーション用 / 読み取り専用）を
  マイグレーション実装へ申し送る。論理設計で「アプリ層で担保する」「履歴は追記専用」と置いた前提は、
  **ロールを分けて初めて成立する**。
- フェーズ2ステップ8で**ログ出力禁止**と判定した属性の一覧を、エラーハンドリング方針
  （`docs/specs/_shared/cross-cutting.md`）と API 詳細設計へ申し送る。

## 逆流ルール（全フェーズ共通）

テーブル・カラムを後から追加・変更するときは、**必ず概念 → 論理 → 物理の順で更新する**。

1. 概念に影響するか判定する（新しい意味を持つ属性か、単なる物理的な最適化か）。
2. 影響するなら `docs/baseline/functional-design.md` の概念モデルを**先に**更新する。
3. 判断（キー・正規化・削除方針・区分値）に影響するなら `logical-data-model.md` を更新する。
4. 最後に `table-definition.md` を追随させる。

物理だけを直すと上流が陳腐化し、次の設計判断が壊れた前提の上に載る。

## 共通の規律

- **正本を重複させない** — 下流は上流を参照し、再定義しない。エンティティ名・区分値・業務ルールは
  上流にある。
- **曖昧な先送りを残さない** — 「物理設計で確定」「実装時に判断」は使えない。
  `docs/specs/3_detail-design/` は詳細設計そのもので、先送り先が無い。
- **1ファイルずつユーザーの承認を得る**（プロジェクト `CLAUDE.md`「ドキュメント作成時」ルール）。
- 相対リンクのパス階層に注意する（`3_detail-design/db/*.md` から baseline へは `../../../baseline/...`、
  `2_basic-design/` へは `../../2_basic-design/...`）。
